SignalBridge

Detection rules that catch identity attacks in the logs a security team already collects: Windows domain controller events and Microsoft Entra ID sign-in and audit logs. I tested them on public attack data I didn't write and compared them with the security community's rules for the same attacks. A lab version, run against real Keycloak, Wazuh, OWASP ZAP and Shuffle, catches access that continues after it was removed.

Decided before the first run

For my first 12 rules, I wrote down which files each should fire on before the first run. That run caught 17 of 22 expected pairs and showed two design flaws, which I fixed instead of loosening any threshold. W5 and its expectations came after; the README describes the first run, but its raw output isn't published.

The attack that hid behind the computer

Kerberoasting run as SYSTEM asks for tickets under the computer's account, which my first draft ignored, like SigmaHQ's rule. My rule now counts every requester and alerts on the burst.

How the lab works

SignalBridge started as a monitor for two of my own apps, BetTail and Netted. For the lab I built two test apps, one for documents and one for expenses, with a deliberate access bug, so a real failure could be caught from start to finish.

Everything runs on one PC: pinned images on an internal Docker network with no internet route, and Shuffle in a separate VM with no network adapter.

Stage 01 / App event

What did the app see?

Each test app sends a small event: which account tried to read which record, and whether it was allowed. Accounts are pseudonyms, and the event has no fields for names, emails, IP addresses or record contents.

Boundary

A signature proves which app sent the event, not that the app reported correctly.

Stage 02 / Signed intake

Can the event be trusted?

Every event is signed with its app's shared secret key (HMAC-SHA-256) and checked against a fixed schema. Events older than 5 minutes are rejected, an exact repeat is accepted once, and a reused ID with different content is refused.

Boundary

Each app can send 600 new events a minute; more are refused.

Stage 03 / Detection rules

Why did this open a case?

Five rules look for repeated failed reads, reads after a permission was removed, slow probing across many records and one record denied to several accounts. Each case keeps the events that triggered it.

Boundary

Activity below a rule's threshold isn't flagged; the evaluation counts those misses.

Stage 04 / Analyst review

Who can close it?

Viewer, analyst and reviewer roles are scoped to each app. Analysts assign the case, open a fix task and import a retest; a different reviewer approves the fix.

Boundary

The console is built for a local lab, not the public internet.

What testing found

Each of these came from a check that failed, and each fix is in the repository. Lessons learned covers the sign-in policy bug and the Wazuh log limit; the write race has its before-and-after record and 13 regression tests.

Detection as code

I rewrote the five lab rules as Sigma, tagged with the MITRE ATT&CK techniques for data taken from information repositories (T1213) and, on the two revocation rules, misuse of valid accounts (T1078). I compiled them with pySigma, Sigma's query converter, and ran them in real engines against the same 48 scenarios. Running them found a problem compiling alone didn't: Splunk refused pySigma's query for one rule.

Access after departure, from AccessOps

AccessOps, my offboarding project, sends signed security events in the Shared Signals standard (CAEP and RISC) when it cuts off a departing employee and when their account is used afterward. SignalBridge polls them over TLS, verifies each signature, issuer and audience, stores each event once and only then acknowledges it.

38 events verified, none refused

Two live rounds against the running AccessOps lab. Each real poll followed a dry run that verified without storing anything.

A critical case when it mattered

In round two, a contained test account was re-enabled and used, and SignalBridge opened a critical "access after departure" case. Round one's 3 critical cases were test-induced: the sender's test backdated each departure by 5 seconds.

Limits

  • The identity rules ran on attack-lab captures through SQLite, not in Splunk or Sentinel. No alerts on the wrong files is a sanity check, not a false-alarm rate for a real network.
  • The lab used synthetic data in an isolated network on one PC; it is not a production deployment.
  • I wrote the 48 evaluation scenarios knowing the rules, so the scores catch regressions rather than measure real-world accuracy.
  • The planned 24-hour run stopped at 10.6 hours of Wazuh capture, and I didn't repeat it.
  • ZAP ran one passive rule on captured traffic, not an active scan.
  • The KQL ran in the Kusto emulator, not Microsoft Sentinel.
