SignalBridge

An access-assurance and detection lab. It watches real authorization paths in two synthetic business apps, detects when someone keeps access they should have lost, and takes an analyst from the finding to an independently verified fix.

Problem

Does access really end after a permission change?

Approach

The problem

When someone is removed from a private group, their access should end. Checking that it actually does usually means pulling together an access test, application logs and a review decision from different places.

SignalBridge brings those steps into one tool. It started with copies of two of my own apps, BetTail and Netted. The October lab uses two synthetic business apps (documents and expenses) with a deliberately injected authorization defect, so a real failure can be detected end to end.

Architecture

Everything ran on one PC: pinned images on an internal Docker network with no internet route, and Shuffle in a separate VM with no network adapter. The console runs behind Waitress on 127.0.0.1. Detection is rule-based, and the running app doesn't use AI. Engineering reference

Stage 01 / Source event

What did the application actually observe?

A fixed contract carries pseudonymous actors, resources and closed operation/outcome values. The adapters must avoid encoding sensitive data in permitted fields.

Boundary

The schema excludes dedicated personal-data and record-content fields; it is not a guarantee that a source tells the truth.

Stage 02 / Signed ingestion

Is the sender known, and is the request valid?

HMAC verification binds the app, key, timestamp and exact body. The collector validates the schema, handles duplicates and commits the queue before acknowledging acceptance.

Boundary

A valid signature identifies a key. It does not certify the underlying observation.

Stage 03 / Rule evaluation

Why did this event produce a case?

Five versioned rules cover repeated failed reads, source-reported boundary changes, authoritative permission-removal correlation, slower probing and same-resource denials across accounts. Cases retain triggering evidence.

Boundary

R4 and R5 add bounded coverage; activity outside their thresholds and missing authoritative context remain gaps. Multiple accounts do not prove coordination.

Stage 04 / Analyst review

Can this person still make the decision?

Viewer, analyst and reviewer roles are scoped per app. Writes re-check membership inside the database transaction; a reviewer cannot approve their own rule proposal.

Boundary

Fourteen live PostgreSQL checks cover two workers, duplicate ingestion, sign-in and reviewer races, concurrent case edits and recovery after an actual process kill. This is component evidence, not high availability or production scale.

Design decisions & tradeoffs

Signed ingestion with a fixed schema

Each event is signed with HMAC-SHA-256 over the app, key ID, timestamp and exact body, compared in constant time and rejected after 5 minutes. Bodies are capped at 16 KiB, and unknown, duplicate or missing fields are rejected. The contract excludes dedicated fields for names, emails, IP addresses, tokens and record contents, and validates allowed fields. This reduces accidental collection; source adapters still need to avoid encoding sensitive data in permitted values.

Reliable delivery

Exact duplicates are acknowledged, but a reused ID with changed content returns 409. Each app is limited to 600 new events per minute (429 beyond that). The queue commits before returning 202, and failed work retries with backoff, then moves to a visible dead-letter state after five failures.

Five rules with declared boundaries

R1 covers repeated unsuccessful private reads; R2 uses source-labeled revocation or regression. R3 correlates authoritative resource-scoped removal with later allowed access, accounting for re-grants and owner rights. R4 requires five distinct denied resources in 30 minutes spanning at least ten minutes. R5 requires six denied reads of one resource by at least three accounts in ten minutes. Versions, controls and limitations are explicit.

Scoped analyst console

Viewer, analyst and reviewer roles are scoped per application, and superusers get no automatic access. The console uses CSRF protection, a no-script CSP, 1-hour HttpOnly SameSite=Strict sessions and login throttling (8 failures per 15 minutes). Reviewers can't approve their own rule changes.

From finding to verified fix

The access run's console database was backed up and restored into a separate database, then used for the whole workflow: acknowledge, assign, create a remediation task and import a retest. The case owner's own review was refused, and an independent reviewer approved the fix. ZAP raised exactly one finding on the faulty build and none on the fixed one; a second run took that finding through the same workflow and confirmed it attached only to the affected app.

Real sign-in, real SIEM

Keycloak handled password and TOTP sign-in for analyst, viewer and reviewer accounts. 28 protocol controls covered callback replay, state tampering, CSRF, per-app scoping, signing-key rotation, back-channel logout and session expiry. A keyboard-only Chromium walkthrough then found that the console's Content-Security-Policy blocked the redirect to the identity provider; the fix has a regression test. Wazuh archived all 24 exported records and raised all 8 expected alerts exactly once.

Automation that can't overreach

A real Shuffle workflow ran nine scenarios against SignalBridge's signed review-task API. The first created one task, and a retry returned the original. A replay, changed content, another app's case and stale evidence were refused, and after a deliberately lost reply the retry recovered the committed task. Shuffle needs Docker-socket access, so it ran only inside a VM with no network adapter.

Work survives a killed worker

In the first PostgreSQL run (9/9), two workers processed 48 queued events across two application scopes without duplicate cases. A child process killed during an uncommitted three-event transaction left all three pending, no partial case survived, and a fresh worker recovered them into one case. The final run (14/14) added duplicate and conflicting ingestion, a sign-in racing a sign-out, and two reviewers deciding at once.

Measure misses as well as alerts

Of 41 scored scenarios, the frozen round found 15 true positives, 6 false positives, 8 misses and 12 true negatives; 7 more were inconclusive. Precision was 15/21 (71%), recall 15/23 (65%) and the false-positive rate 6/18 (33%). The scenarios were written with knowledge of the rules, so this is regression evidence, not a blind benchmark.

Frozen evaluation · Rule catalog

Long runs and monitoring

A compressed 40-minute version of the 24-hour schedule ran all five planned interruptions, from stopped workers to a stopped Wazuh connector: all 1,201 reads were delivered and seen by Wazuh exactly once. A continuous run then delivered all 27,118 reads over 13.5 hours. Prometheus and Grafana passed 24 controls showing the dashboards stayed accurate through a backlog and recovery.

Rehearsal · Continuous run · Monitoring

Lessons learned lists the bugs these runs found that unit tests had missed, and how each was fixed. Public CI runs the core checks on every change. An axe accessibility scan found 0 violations on 19 console and portfolio pages in light and dark mode, after fixing six issue types.

Detection rules as code

The five rules also exist as Sigma rules with MITRE ATT&CK tags: T1213 for all five, and T1078 for R2 and R3. pySigma compiles four of them to Splunk SPL and one to Microsoft Sentinel KQL; the Kusto backend can't compile correlation rules, so the rest are hand-written and labeled as such.

  • 48/48scenarios where the KQL matched the Python rules, run in Microsoft’s Kusto emulator
  • 45/48for hand-written SPL in a local Splunk Free instance; Splunk leaves out events exactly on a window edge
  • 45/48for the compiled Sigma rules executed in SQLite; the 3 differences are R3 re-grants, which Sigma can’t express
  • 40/48for pySigma’s generated SPL: Splunk rejected its R5 query, and fixed time bins missed two edge cases

Running the queries in real engines found what compiling alone didn’t. pySigma’s Splunk backend generates R5 as a multisearch with stats inside it, which Splunk refuses; the hand-written SPL uses rolling windows instead of fixed bins. The Python rules, replayed, still reproduce the published evaluation in 48 of 48 scenarios.

A GitHub Actions workflow checks the hash-pinned tooling, linting, the compiled queries, the replay report and receipt consistency on every relevant change. These are local, single-node engines with synthetic events, and the KQL ran in the Kusto emulator, not in Microsoft Sentinel. The scenarios are the same 48 builder-written ones as the evaluation, so this compares rule logic, not accuracy.

Access after departure, from AccessOps

AccessOps, my offboarding project, signs Shared Signals events (SSF 1.0 with CAEP and RISC, ES256) when it contains a departing employee and when that person's account is used afterward. SignalBridge polls them over TLS with a pinned certificate authority, verifies each token's signature, issuer, audience and claims, stores it once and acknowledges it only after storing it. AccessOps treats a refused token as final, so every real poll follows a dry run that verifies without storing or acknowledging anything.

In two live rounds, SignalBridge verified 38 events and refused none. The genuine detection came in round two: an AccessOps check re-enabled a contained test account and signed in with it, and SignalBridge opened a critical "access after departure" case. Three first-round cases were test-induced, because an AccessOps test backdated departures by five seconds. They stay on record, labeled as such.

Earlier findings

September 2026 checks from the first version of the lab, kept with their dates. Builder-run, not an independent evaluation.

Wazuh replay. I sent application events through a recoverable ledger to a Wazuh 4.14.8 manager running custom rules. In the retained September 25 replay, all 64 records arrived: 31 expected alerts and 33 expected non-alerts, with nothing missing or duplicated. The retained input receipt comprises 14 observed lab events, 24 synthetic events and 26 legacy events whose provenance remains unclassified.

OWASP ZAP outage. When I took the scan target offline on purpose, the run was recorded as failed rather than as a clean scan. A retry then passed with 3 requests and 5 findings across 3 rules. Importing the same report twice doesn't create duplicates.

  • 16/16rule-contract checks in a pre-declared challenge

Scanner-triage scope: the retained triage receipt classifies 18 findings as 16 false positives, one open default-credential finding and one reviewed container-listener finding. The reviewed listener was not a verified deployment result. Credential remediation is documented separately below.

Finding: default password in the lab

Scanner triage found a default database password and containers with no resource limits exposing backend ports. I rotated all 8 database role credentials (32 checks, including rejection of the old default), capped the services' memory and CPU, removed the backend port bindings, and retested every route and service.

Finding: access-withdrawal race

A time-of-check to time-of-use gap let a user whose access had just been removed complete 4 case writes. The fix re-checks the account and role inside the database transaction before locking the record. Moving the check to the write boundary closes this demonstrated gap. This result used SQLite; the October PostgreSQL runs later covered concurrent case and review writes. Cases, rule replay, scanner imports and practice records all use that check now, covered by 13 regression tests.

Limits

  • Synthetic data in an isolated lab on one PC. This is not a production deployment, a high-availability system or a replacement for enterprise tools.
  • The full 24-hour run was not completed. Wazuh's collector stopped at 10.6 hours on a log-folder limit, since fixed, and I chose not to repeat the day.
  • Detection numbers come from scenarios written with knowledge of the rules: regression evidence, not independent accuracy.
  • The September challenge found three patterns R1 missed: slow probing, probing spread across accounts, and revocations that don't name the affected member. Rules R3–R5 cover bounded versions of them, and the 48-scenario round still records misses.
  • ZAP analyzed captured authenticated responses with one passive rule; it is not an active scan. The Shuffle run is one fixed workflow with one HTTP action.
  • The console trusts local administrators and must not be exposed publicly.

AI use. AI coding agents wrote much of the code and documentation under my direction. The app itself doesn't use AI; detection is rule-based and a person decides each case.
