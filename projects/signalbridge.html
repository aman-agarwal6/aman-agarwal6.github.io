SignalBridge

A detection lab that catches access that should have ended. Two test apps send signed events about who tried to read what; five detection rules flag access that continues after a permission was removed, and an analyst takes each finding to a verified fix. I ran it against real Keycloak, Wazuh, OWASP ZAP and Shuffle in an isolated lab.

What it shows

Detection engineering

Five versioned rules, rewritten as Sigma with MITRE ATT&CK tags, then run as SPL in Splunk and as KQL in a Kusto emulator.

Real security tools

Keycloak sign-in with MFA, a Wazuh SIEM, OWASP ZAP scans and a Shuffle SOAR workflow, all in an isolated lab.

From alert to fix

Each finding goes from case to analyst review to a retest, and nobody can approve their own fix.

Reliable event intake

Signed, de-duplicated events that survived a killed worker, a stopped collector and a 13.5-hour run.

How it works

SignalBridge started as a monitor for two of my own apps, BetTail and Netted. For the lab I built two test apps, one for documents and one for expenses, with a deliberate access bug, so a real failure could be caught from start to finish.

Everything runs on one PC: pinned images on an internal Docker network with no internet route, and Shuffle in a separate VM with no network adapter.

Stage 01 / App event

What did the app see?

Each test app sends a small event: which account tried to read which record, and whether it was allowed. Accounts are pseudonyms, and the event has no fields for names, emails, IP addresses or record contents.

Boundary

A signature proves which app sent the event, not that the app reported correctly.

Stage 02 / Signed intake

Can the event be trusted?

Every event is signed with HMAC-SHA-256 and checked against a fixed schema. Events older than 5 minutes are rejected, an exact repeat is accepted once, and a reused ID with different content is refused.

Boundary

Each app can send 600 new events a minute; more are refused.

Stage 03 / Detection rules

Why did this open a case?

Five rules look for repeated failed reads, reads after a permission was removed, slow probing across many records and one record denied to several accounts. Each case keeps the events that triggered it.

Boundary

Activity below a rule's threshold isn't flagged; the evaluation counts those misses.

Stage 04 / Analyst review

Who can close it?

Viewer, analyst and reviewer roles are scoped to each app. Analysts assign the case, open a fix task and import a retest; a different reviewer approves the fix.

Boundary

The console is built for a local lab, not the public internet.

Detection as code

I rewrote the five rules as Sigma with MITRE ATT&CK tags (T1213, plus T1078 for the two revocation rules), compiled them with pySigma and ran them in real engines against the same 48 scenarios. Running them found a problem compiling alone didn't: Splunk refused pySigma's query for one rule.

Access after departure, from AccessOps

AccessOps, my offboarding project, sends signed Shared Signals events (CAEP and RISC) when it cuts off a departing employee and when their account is used afterward. SignalBridge polls them over TLS, verifies each signature, issuer and audience, stores each event once and only then acknowledges it.

38 events verified, none refused

Two live rounds against the running AccessOps lab. Each real poll followed a dry run that verified without storing anything.

A critical case when it mattered

In round two, a contained test account was re-enabled and used, and SignalBridge opened a critical "access after departure" case.

Limits

  • Synthetic data in an isolated lab on one PC; not a production deployment.
  • I wrote the 48 evaluation scenarios knowing the rules, so the scores catch regressions rather than measure real-world accuracy.
  • The planned 24-hour run stopped at 10.6 hours of Wazuh capture, and I didn't repeat it.
  • ZAP ran one passive rule on captured traffic, not an active scan.
  • The KQL ran in the Kusto emulator, not Microsoft Sentinel.
