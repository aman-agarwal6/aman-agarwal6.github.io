SignalBridge

A security assurance workbench that connects what an application is supposed to protect to recorded proof that it does, from access tests and signed telemetry through detection, investigation and retest.

The problem

When someone leaves a private group, their access should stop. Proving that it actually does takes three things that usually live in different places: an access test, telemetry from the application, and a documented review decision. Security teams end up assembling that evidence by hand.

I built SignalBridge to join them into one workflow, using two of my own applications (BetTail and Netted) as the systems under test: requirement → authorization test → metadata event → investigation → correction → retest.

Architecture

Django renders the console behind Waitress on 127.0.0.1 only. No production telemetry, no AI at runtime: rules are deterministic and people make the review decisions.

Key engineering decisions

Signed, closed-schema ingestion

Each event is signed with HMAC-SHA-256 over the app, key ID, timestamp and exact body, compared in constant time and rejected after 5 minutes. Bodies are capped at 16 KiB, and unknown, duplicate or missing fields fail. The schema has no field for names, emails, IPs or tokens, so private data can't leak into telemetry.

Delivery that can't silently lose data

Exact duplicates are acknowledged, but a reused ID with changed content returns 409. Each app is limited to 600 new events per minute (429 beyond that). The queue commits before returning 202, and failed work retries with backoff, then moves to a visible dead-letter state after five failures.

Two deterministic detection rules

R1: one actor is denied (or can't see) 3+ distinct private records within a rolling 5-minute window. R2: an allowed private read is reported after a membership removal or policy regression, which opens a critical-priority case. Each rule shows the exact evidence that triggered it.

Least-privilege analyst console

Viewer, analyst and reviewer roles are scoped per application, and even superusers get no implicit bypass. The console uses CSRF protection, a no-script CSP, 1-hour HttpOnly SameSite=Strict sessions and login throttling (8 failures per 15 minutes). Reviewers can't approve their own rule changes.

Real tool integrations

Wazuh SIEM. I exported application metadata through a recoverable ledger into a Wazuh 4.14.8 manager running custom rules. The run delivered all 64 records with the 31 expected alerts and 33 expected non-alerts, with zero missing or duplicated records. A separate recovery run restarted the collector twice mid-stream without losing or duplicating an input.

OWASP ZAP. During a deliberate target outage, the scan was recorded as failed and incomplete rather than clean. That's the behavior you want, because a failed scan shouldn't look like "no findings." A fresh retry passed (3 requests, 5 findings across 3 rules), and repeat imports are idempotent.

Results

  • 1,083automated tests (1,030 Python, 53 Node), 0 failures or skips
  • 15/15offline detection scenarios; 600 benign events, 0 false alerts
  • 16/16rule-contract checks in a pre-declared challenge
  • 18scanner leads triaged: 16 false positives, 1 real lab issue fixed

Finding: default password in the lab

Scanner triage turned up a default database password and unbounded containers exposing backend ports. After approving the repair, I rotated all 8 database role credentials (32 checks, including rejection of the old default), capped the services' memory and CPU, removed the backend port bindings, and retested every route and service.

Finding: access-withdrawal race

A time-of-check/time-of-use gap let a user whose access had just been withdrawn complete 4 case writes. The fix re-checks the account and role inside the database transaction before locking the target. Cases, rule replay, scanner imports and practice records now share that guard, backed by 13 regression tests.

Known limits and what I'd do next

I wrote three harder attack patterns into the challenge on purpose, and none of them alerted. I report that result next to the passes:

  • Slow probing spread over 6 minutes escapes R1's 5-minute window.
  • Distributed activity across several accounts escapes per-actor correlation.
  • Missing revocation context: the telemetry lacks an authoritative link between a membership change and the affected reader.

Next steps: richer source context, independently written test cases instead of builder-authored ones, continuous collection rather than recorded runs, and finishing the Shuffle SOAR integration, which is paused after a storage startup failure.

How AI was used. AI coding agents wrote much of the implementation and documentation under my direction. The running product uses no AI: detection is rule-based and every disposition is a human decision.
