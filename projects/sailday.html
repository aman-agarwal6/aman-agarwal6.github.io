Price tracking, from public rate to booking comparison

Alongside itineraries and checklists, Sailday monitors public cruise prices and keeps a record of how they change. The configured dashboard covers interior cabins, ocean-view balconies, the Deluxe Beverage Package and VOOM internet. Travelers can inspect historical checks, compare eligible rates with their saved booking or receipt, and opt into price-change notifications.

These values are invented and never contact Royal or read a booking. The actual tracker also checks sailing, category, guest compatibility and quote completeness. A public-rate difference is indicative; personal offers and repricing eligibility require confirmation.

1. Collect public rates

PostgreSQL collectors use Royal Caribbean’s public sailing-price endpoint for rooms and its unauthenticated Cruise Planner catalog for drinks and internet. Supabase pg_cron schedules three hourly collection jobs; they run while the app and personal computer are closed.

An authorized Check latest prices action can request a new collection. Scheduled and manual checks share a locked 15-minute cooldown per source. Ordinary page refreshes read saved observations rather than making extra requests to Royal.

2. Validate and compare

Room matching requires the configured sailing and an explicit choose-your-room category; guarantee and unknown-assignment quotes are excluded. Stable category identities preserve history when provider labels change. Room comparisons use the booked fare plus taxes, rather than the deposit paid.

Beverage comparisons retain the original receipt and normalize it by guests and days. The public daily-rate estimate applies 18% gratuity once; full-order estimates round after multiplication. Public starting rates remain distinct from confirmed, account-specific quotes.

3. Preserve history and show trends

PostgreSQL retains timestamped checks. React renders SVG graphs with an exact-check selector, high/low values and a booking or purchase reference line. Missing quotes, changed billing units and gaps between checks break the graph instead of creating false zero-price drops.

The device keeps a bounded copy of price changes for offline use. Failed requests retain successful saved prices, and delayed responses cannot replace a newer confirmed observation. Open graphs refresh as newer checks arrive.

4. Notify on selected changes

The booking owner can opt in each device and choose products, change direction and a minimum dollar change. Alerts compare collected source rates; the beverage card’s gratuity-adjusted estimate is separate. First observations, unchanged prices and failed collections do not create price-change alerts.

Supabase queues the jobs and wakes a Vercel function through pg_net. The web-push library sends encrypted Web Push, with bounded retries and expired-subscription handling. Delivery to the phone still depends on permission, connectivity and operating-system settings.

Technology: React and custom SVG charts; Zod validation; Supabase/PostgreSQL, SQL HTTP requests, pg_cron and pg_net; Vercel and encrypted Web Push. Scheduled price checks use public source data without an AI model, a paid price feed or Royal account credentials.

The automatic feeds currently cover one configured sailing, rather than a general cruise catalog. Other watched items use reviewed manual quotes or price-history JSON imports. Advertised prices can change between checks; personal offers, final checkout totals, exact cabin availability and repricing eligibility require confirmation with Royal. No purchase or automatic rebooking is performed.

Permissions remain a server decision

Groups have owner, editor and viewer roles. PostgreSQL checks the signed-in identity and current membership; direct client writes to application tables are denied. Edit operations lock the group before checking the role, so membership changes and writes use the same serialization boundary.

Invites are expiring, limited-use capabilities. The server stores their hashes and validates revocation and usage limits before granting membership. Realtime broadcasts signal a change without sending private rows; clients reload through a new membership check.

A queued edit is not a confirmed save

Offline edits and messages stay in a durable outbox. Each operation carries an identity for retry handling. Independent field edits can merge, while competing edits to the same field require a user decision. The interface preserves pending work and reports connection problems instead of claiming synchronization succeeded.

Server authorization is checked when a queued operation arrives. Removing a member blocks future server access, but downloaded copies remain on that person’s device. The product documentation makes that data-lifecycle boundary explicit.

Updates preserve the working application

The service worker caches a complete application shell and retains a previous complete version. Updates wait while a dialog, editing field or unsent chat draft is active. Authentication and API responses are excluded from the application-shell cache.

Travel documents stay on each device. Plan backups exclude chat, credentials, invitations and files. Public itinerary lookups use bounded requests and allowlisted destinations; redirects are checked before another fetch. Public price checks use cooldowns and preserve the last successful observation when a request fails.

What the evidence establishes

The source review covers price collectors, comparisons, graphs, notification delivery, group-access migrations, synchronization code and service-worker behavior. Retained tracker tests use synthetic HTTP, booking records and browser transport to exercise matching, cooldowns, failure recovery and offline views; notification encryption checks use disposable keys without sending a live message. The retained release records describe isolated browser checks; simulated identities and database transport do not establish a real two-phone sign-in test.

  • Browser storage can be removed by the user, private browsing or operating-system storage pressure. Offline copies need a separate backup.
  • Revocation cannot erase information already downloaded by a group member.
  • Physical phone installation, storage eviction and OS restart behavior require device testing.
  • Public-source availability and hosting quotas bound remote lookups.
