Permissions remain a server decision

Groups have owner, editor and viewer roles. PostgreSQL checks the signed-in identity and current membership; direct client writes to application tables are denied. Edit operations lock the group before checking the role, so membership changes and writes use the same serialization boundary.

Invites are expiring, limited-use capabilities. The server stores their hashes and validates revocation and usage limits before granting membership. Realtime broadcasts signal a change without sending private rows; clients reload through a new membership check.

A queued edit is not a confirmed save

Offline edits and messages stay in a durable outbox. Each operation carries an identity for retry handling. Independent field edits can merge, while competing edits to the same field require a user decision. The interface preserves pending work and reports connection problems instead of claiming synchronization succeeded.

Server authorization is checked when a queued operation arrives. Removing a member blocks future server access, but downloaded copies remain on that person’s device. The product documentation makes that data-lifecycle boundary explicit.

Updates preserve the working application

The service worker caches a complete application shell and retains a previous complete version. Updates wait while a dialog, editing field or unsent chat draft is active. Authentication and API responses are excluded from the application-shell cache.

Travel documents stay on each device. Plan backups exclude chat, credentials, invitations and files. Public itinerary lookups use bounded requests and allowlisted destinations; redirects are checked before another fetch. Public price checks use cooldowns and preserve the last successful observation when a request fails.

What the evidence establishes

The source review covers group-access migrations, synchronization code, service-worker behavior, and tests for offline reopening and multiple synthetic users. The retained release records describe isolated browser checks; simulated identities and database transport do not establish a real two-phone sign-in test.

  • Browser storage can be removed by the user, private browsing or operating-system storage pressure. Offline copies need a separate backup.
  • Revocation cannot erase information already downloaded by a group member.
  • Physical phone installation, storage eviction and OS restart behavior require device testing.
  • Public-source availability and hosting quotas bound remote lookups.
