AccessOps

When someone leaves, disabling their account is the easy part. Their sessions, tokens, group rights and Kerberos tickets can keep working. AccessOps ends that access in every system it can reach as soon as a signed HR event arrives, reads each system back to prove it changed, and keeps everything else open as owned work until an independent reviewer closes the case.

Problem

A disabled account still leaves sessions, tokens and group rights working. What proves a leaver's access ended?

Approach

Contain from a signed HR event, read every system back, and close only on someone else's review.

Evidence

HR event to tokens refused in 2.6 s; Entra read back through Graph in 20 s; six gaps found by live runs; signed v0.3.0 release.

Local lab, a free Entra test tenant and a public demo. Synthetic people only; not a production deployment.

What it shows

Identity lifecycle across three real systems

Leaver automation in Keycloak (OIDC, SCIM, back-channel logout), Microsoft Entra ID (Microsoft Graph with a certificate credential) and a Samba AD-compatible directory (LDAPS, Kerberos). Automated agents the person sponsors are suspended in the same step, and nothing counts as done until the system is read back.

Testing that finds what disabling misses

Before-and-after checks against the live services found six gaps, from a surviving group membership to Kerberos tickets that keep working for 10 hours. Each was fixed or is stated on the case, and the failed runs stay published.

Security engineering and detection

Operators need a second factor, checked by the identity provider and again by the backend. OPA policy denies when it is unavailable. Keys rotate without refusing a valid token, and a sign-in after departure reaches the SOC as a signed event in 32 s.

Controls an auditor recognizes

Separation of duties: case owners can't close their own case, and approvals bind the exact change and expire in 15 minutes. Mapped to NIST SP 800-53 PS-4, AC-2, AC-5 and IA-2(1), and shipped through protected pull requests and signed releases.

The problem

Offboarding usually ends when someone disables the main account and closes the ticket. The person can still be signed in to apps, hold tokens that apps accept, keep group rights and Kerberos tickets, and reach repositories, shared credentials and data that nobody has handed over. Auditors still ask for proof that access ended on time.

AccessOps makes that gap visible and closes what it can. Each departure becomes a case with an owner, a four-hour target and a required action for every system: nine actions, or ten with an enrolled directory account. Every action records where its evidence came from, and unknown never counts as removed.

How a case closes

Keycloak and the directory run on loopback in a local Docker lab; the Entra connector calls Microsoft Graph for a free test tenant only. The public demo is a separate browser simulation of the same case rules and never calls either.

Stage 01 / Contain

Can the person still act in this system right now?

One transaction revokes the person's grants and suspends the agents they sponsor. Keycloak removals are queued for every known managed grant, including ones revoked earlier; an enrolled directory account is disabled and removed from its mapped groups. The person's Keycloak sessions end too, which signs them out of apps that accept back-channel logout, and apps that check tokens themselves get a signed revocation event and refuse the person's earlier tokens.

Boundary

Containment stops new local actions. It does not recall work an agent already started.

Stage 02 / Read back

Did the provider actually change?

The worker reads before it retries and records when each reading was taken. A disabled account and each removed membership need their own fresh observation; directory writes target immutable GUIDs and update account flags atomically. For a day afterward, the person's sign-ins are read as well; any success adds an investigation the case can't close without.

Boundary

Readings older than two hours, unknown or partial results reopen the action.

Stage 03 / Account for the rest

What about Entra, GitHub, Microsoft 365 and shared credentials?

An enrolled Entra account is disabled, removed from its groups and has its sign-in sessions revoked through Microsoft Graph, then read back. For other platforms, bounded reports are imported for explicitly bound account IDs, never matched by name or email. Work no report can prove becomes a written owner statement, labeled as such.

Boundary

Absence from a GitHub list is unknown, not removed. Entra state does not prove application sessions ended.

Stage 04 / Close

Who can say the case is done?

A reviewer who neither owns the case nor submitted evidence accepts the exact revision and packet hash. The closed packet cannot be changed afterward.

Boundary

Closure is an administrative record of reviewed evidence, not proof that every copy or session is gone.

What the live runs caught

Each gap was found by a before-and-after check that failed against the live services. The failed runs stay on the demo's evidence page beside the fix.

One failure was the test's. The first post-departure check flagged the test's own sign-in, made seconds after a departure time the test had backdated. A sign-in after the effective time is access after departure, even before containment finishes, so the test changed, not the rule.

Design decisions & tradeoffs

Evidence labels that never upgrade

Every action shows one of five sources: signed CI evidence, provider observation, imported snapshot, owner attestation or simulated. Each has a fixed icon, label and color. A statement can't become proof, and a browser reading can't pass for a lab one.

Approvals bound to the exact change

Access grants need an independent approver whose decision binds the exact change and policy version and expires after 15 minutes. Containment acts immediately. Policy outages and unknown connector results deny.

Connectors that can only touch what they own

The directory connector can change two properties on the exact objects created for it, and live checks confirm it cannot touch canary accounts. The Entra connector acts only on listed test objects and refused the tenant administrator and an unlisted user in the live run.

An interface built around the next step

Each case shows one next step. When the current role can't take it, the case says who can instead of hiding the button. Dark and light themes share one token set, and automated WCAG checks run on every page in both.

Limits and next steps

  • Microsoft Entra was tested only in a free test tenant with synthetic users. Its sign-in logs need a paid tier, so access after departure is watched in Keycloak only. Microsoft 365 and GitHub appear as offline fixtures and owner statements.
  • Samba results do not prove Microsoft Active Directory interoperability.
  • An app that checks tokens itself refuses a leaver's token early only if it follows AccessOps' revocation signals. Directory connections and Kerberos tickets from before containment keep working until they expire, up to 10 hours.
  • Operators use a software one-time-code authenticator, not a phishing-resistant key.
  • This is a reference system with synthetic data, not a production deployment. The NIST mapping is a selected engineering mapping, not a compliance claim.

AI use. AI coding agents wrote much of the code and documentation under my direction. The application itself doesn't use a language model; its review assistant is deterministic and can only propose, never approve.
