The problem

Friend groups share bets as screenshots in group chats, which makes it hard to see who is up, whose picks are worth following and what's still pending. The records involve real money and private groups, so they need to be accurate and private.

BetTail gives each group one shared record. Members post a pick (typed, pasted from a sportsbook link or read from a screenshot), others can follow it with their own stake and odds, and the database calculates profit, ROI, units, drawdown and leaderboards.

Architecture

The app has no service-role key. Every request runs as the signed-in user, so row-level security applies even if someone calls the database directly.

Stage 01 / Member action

What is the browser asking to change?

A member proposes a pick or financial update. Screenshot OCR and imported fields remain untrusted and reviewable. The browser is not the authority for ownership or money totals.

Boundary

An interface check alone cannot protect direct API calls.

Stage 02 / Request boundary

Which user is making this request?

The server authenticates the caller, checks request origin and bounds inputs. The normal runtime does not need a service-role database key.

Boundary

These checks do not replace authorization inside the database.

Stage 03 / Database write

Does membership still permit this exact operation?

Guarded SQL functions derive identity from the session. Integer-cent calculations, transaction boundaries, receipts and stale-update checks keep retried writes from double-posting.

Boundary

More application logic in SQL makes migration review and real database tests essential.

Stage 04 / Private realtime

What information leaves the database?

Realtime messages signal that something changed without including private rows. Clients reload through a membership-checked query.

Boundary

Per-account rate limits do not stop a distributed attack; builder-led review is not an independent assessment.

Design decisions & tradeoffs

Access control in the database

Row-level security is on for every exposed table, and direct client writes are denied. Writes go through authenticated database functions that derive identity from the session, not from anything the client sends. Default privileges are revoked, so future tables start private. Centralizing writes makes the authorization boundary testable, but puts more application logic in SQL migrations that need careful review.

Accurate money records

Amounts are stored as integer cents, and profit is calculated in SQL as the single source of truth. Every write carries a caller-generated UUID and a receipt, so a retried request can't double-post. Settlement checks the expected timestamp to block stale overwrites. All financial changes are transactional and audited.

Private realtime updates

Realtime messages contain no row data, only a signal that something changed. Clients reload through a membership-checked query, so someone removed from a group can't receive its private records, even before their channel authorization refreshes.

Rate limits and input checks

PostgreSQL enforces 8 invite-code guesses and 60 writes per minute per user, along with request-origin checks and body-size limits. Screenshot OCR is treated as untrusted input: extracted numbers need corroborating ticket text, and every inferred field stays reviewable.

The AI research agent

BetTail's NFL tab is filled by Downfield, a separate local worker that runs a subscription-authenticated LLM to write structured game reports. Most of the work went into controlling and checking its output:

  • Restricted runs: before each run, the worker verifies the sign-in method and model. The child process gets a minimal environment allowlist (no API keys or tokens), only web search and fetch tools are allowed, and any unexpected tool or model aborts the run.
  • Validated output: every report must pass JSON Schema validation plus arithmetic and cross-player consistency checks (for example, receiving yardage has to reconcile with passing yardage).
  • Source tracking: a citation counts as verified only if the agent actually fetched that exact URL. Unverified sources are labeled and lower the report's confidence. Web pages are treated as untrusted evidence, never as instructions.
  • Grading: after each game, code grades the predictions against final statistics. Missing statistics stay ungraded rather than being guessed.

The app labels the model's probabilities as uncalibrated. BetTail doesn't place wagers.

Testing and delivery

Database tests execute the actual SQL migrations in PGlite (embedded PostgreSQL), so roles, grants, row-level security, constraints and transactions are tested directly instead of mocked. Browser tests use synthetic fixtures and never touch real members' records.

Known limits

  • Database rate limits stop a single abusive account, not a distributed attack.
  • The sportsbook handoff still needs testing on physical iOS and Android devices.
  • The security review was self-directed, not an independent assessment.
