BetTail

A live web app where private groups share, track and settle sports picks across sportsbooks. I built it like a financial system, then added an LLM research agent with strict guardrails.

The problem

Friend groups share bets as screenshots in group chats, so nobody knows who is actually up, whose picks are worth following, or what's still pending. The records involve real money and belong to private groups, so accuracy and privacy aren't optional.

BetTail gives each group one shared record: post a pick (typed, pasted from a sportsbook link, or read from a screenshot), let others "tail" it with their own stake and odds, settle results, and see realized profit, ROI, units, drawdown and leaderboards, all computed in the database.

Architecture

The app holds no service-role key: every request runs under the signed-in user's own database identity, so row-level security still applies even if someone bypasses the Next.js API.

Key engineering decisions

The database is the security boundary

Row-level security is on for every exposed table, and direct client writes are denied. All changes go through one authenticated gateway function that derives identity from the session, not from anything the client sends. Default privileges are revoked, so future tables start private.

Money handled like money

Amounts are stored as integer cents, and profit is calculated in SQL as the single source of truth. Every write carries a caller-generated UUID and a receipt, so a retried request can't double-post. Settlement checks the expected timestamp to block stale overwrites. All financial changes are transactional and audited.

Private realtime by design

Realtime messages carry no row data, just a "something changed" signal. Clients reload through a membership-checked query, so someone removed from a group can't receive its private records, even before their channel authorization refreshes.

Abuse limits in the database

PostgreSQL enforces 8 invite-code guesses and 60 writes per minute per user, along with request-origin checks and body-size limits. Screenshot OCR is treated as untrusted input: extracted numbers need corroborating ticket text, and every inferred field stays reviewable.

The AI research agent

BetTail's NFL tab is filled by a separate research worker that runs an LLM (Claude, through the Claude Code CLI) to write structured game reports. The interesting part is the guardrails, not the model:

  • Locked-down execution: before each run, the worker verifies the sign-in method and model. The child process gets a minimal environment allowlist (no API keys or tokens), only web search and fetch tools are allowed, and any unexpected tool or model aborts the run.
  • Schema-validated output: every report must pass a 60–75 kB JSON Schema plus arithmetic and cross-player consistency checks (for example, receiving yardage has to reconcile with passing yardage).
  • Source provenance: a citation counts as verified only if the agent actually fetched that exact URL. Unverified sources are labeled and lower the report's confidence. Web pages are treated as untrusted evidence, never as instructions.
  • Deterministic grading: after each game, predictions are graded against final statistics by code, not by the model. Missing statistics stay ungraded rather than being guessed.

The model's probabilities are uncalibrated judgments, and the app states that. BetTail never places wagers.

Testing and delivery

  • 320–1440pxlayouts checked, plus keyboard and 200% text

Database tests execute the actual SQL migrations in PGlite (embedded PostgreSQL), so roles, grants, row-level security, constraints and transactions are exercised for real rather than mocked. Browser tests use synthetic fixtures and never touch real members' records.

Known limits

  • Database rate limits stop a single abusive account, not a distributed attack.
  • The sportsbook handoff still needs testing on physical iOS and Android devices.
  • The security review was self-directed, not an independent assessment.
