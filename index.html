Stage 01 / Source event

What did the application actually observe?

A fixed contract carries pseudonymous actors, resources and closed operation/outcome values. The adapters must avoid encoding sensitive data in permitted fields.

Boundary

The schema excludes dedicated personal-data and record-content fields; it is not a guarantee that a source tells the truth.

Stage 02 / Signed ingestion

Is the sender known, and is the request valid?

HMAC verification binds the app, key, timestamp and exact body. The collector validates the schema, handles duplicates and commits the queue before acknowledging acceptance.

Boundary

A valid signature identifies a key. It does not certify the underlying observation.

Stage 03 / Rule evaluation

Why did this event produce a case?

The published snapshot checks repeated unsuccessful private reads and source-labeled reads after a boundary change. Cases retain the triggering evidence.

Boundary

Slow probing, distributed accounts and missing affected-member context did not alert in the documented challenge.

Stage 04 / Analyst review

Can this person still make the decision?

Viewer, analyst and reviewer roles are scoped per app. Writes re-check membership inside the database transaction; a reviewer cannot approve their own rule proposal.

Boundary

The demonstrated write race is fixed in the local SQLite workflow. PostgreSQL concurrency behavior is not established.

What the replay measured+

The retained September 25 Wazuh replay reconciled 64/64 records, with 31 expected alerts and 33 expected non-alerts. It is a local historical replay, not a fresh run or production telemetry.

The failure that changed the design+

A time-of-check/time-of-use gap allowed four local case writes after access was withdrawn. The write now re-checks account and role inside the transaction; the case study documents 13 regression tests.

What the tests do not establish+

The builder knew the rules while writing the scenarios. The published challenge documents three harder patterns that did not alert. An independent evaluation and continuous collection are separate next steps.

Deployed application; builder-led security review. It tracks wagers and does not place them.

Stage 01 / Member action

What is the browser asking to change?

A member proposes a pick or financial update. Screenshot OCR and imported fields remain untrusted and reviewable. The browser is not the authority for ownership or money totals.

Boundary

An interface check alone cannot protect direct API calls.

Stage 02 / Request boundary

Which user is making this request?

The server authenticates the caller, checks request origin and bounds inputs. The normal runtime does not need a service-role database key.

Boundary

These checks do not replace authorization inside the database.

Stage 03 / Database write

Does membership still permit this exact operation?

Guarded SQL functions derive identity from the session. Integer-cent calculations, transaction boundaries, receipts and stale-update checks keep retried writes from double-posting.

Boundary

More application logic in SQL makes migration review and real database tests essential.

Stage 04 / Private realtime

What information leaves the database?

Realtime messages signal that something changed without including private rows. Clients reload through a membership-checked query.

Boundary

Per-account rate limits do not stop a distributed attack; builder-led review is not an independent assessment.

A concrete review finding+

A SQL NULL value could bypass a cache-only branch. Explicit NULL handling and a regression test were added. The case study also explains privilege defaults, cookies and CSV formula protection.

Why database tests matter+

The retained review used the actual migrations in embedded PostgreSQL to test roles, grants, constraints and transactions. Its dated counts were not rerun for this portfolio pass.

Where applied AI belongs+

The NFL tab consumes reports from Downfield, a separate local research worker with a limited publication connection. The browser app does not grant that worker general database access.

Stage 01 / Local import

What should leave the user’s device?

In the reviewed cloud edition, raw brokerage CSV/PDF content is parsed in the browser. Only reviewed, selected trade records are saved.

Boundary

A compromised browser can still read open content; the local-storage edition has a different persistence model.

Stage 02 / Reviewed records

What does this transaction mean?

Cost basis, fees and realized profit are explicit. Missing cost basis goes to review instead of being guessed; contribution weights are fixed at purchase time.

Boundary

The contribution convention is not a unitized NAV valuation.

Stage 03 / Guarded cloud access

Can this user access these records?

The dated cloud review covers verified identity, a live session, authenticator-level assurance, ownership checks and denied direct table operations.

Boundary

These are the September 11–13 cloud-review controls, not a claim about every edition or every possible attack.

Stage 04 / Journal & recovery

Can restored records be reconciled?

Corrections preserve history through reversals and replacements. A recorded isolated restore matched 506 original journal records, including cent totals and hashes.

Boundary

The journal drill did not restore the complete hosted service or authentication. Operational readiness remains open.

Evidence & judgment

Go one level deeper.

Recorded results, decisions and limitations. Expand what interests you.

A recovery result with a boundary+

The September 13 recovery drill matched 506/506 original journal records in an isolated local database. It is not a full hosted-service restore or a demonstrated recovery-time guarantee.

The assessment’s release conditions+

Administrator access review, recoverable backups, hosting eligibility and independent review still need closure evidence in the dated assessment.

The accounting tradeoff+

Purchase-date contribution weights are easier to explain and audit. They should not be presented as NAV-based fund accounting, and missing basis is never invented.

Stage 01 / Evidence packet

What is known before the model starts?

Public game, player, injury, news and weather observations are assembled with source snapshots and named gaps. Original input and optional price observations are retained.

Boundary

A cached screen cannot establish fresh injury information or current price availability.

Stage 02 / Research worker

What authority does the model receive?

A subscription-authenticated local CLI runs with fixed settings, bounded inputs, restricted tools and an environment allowlist. Fresh work depends on the computer being awake and online.

Boundary

Webpages are untrusted evidence, not instructions. A permitted fetch does not prove the page supports the claim.

Stage 03 / Deterministic checks

Is the report internally consistent?

The contract checks shape, identities, retained baselines, arithmetic, source provenance and broad cross-player totals. Missing estimates and unverified citations remain visible.

Boundary

Schema validity and consistent arithmetic do not establish correct football assumptions or a forecasting edge.

Stage 04 / Version & publish

What changes when the forecast changes?

Each report preserves its evidence and price snapshots. A separate, expiring report-only capability sends football reports to BetTail; grading can leave missing statistics ungraded.

Boundary

This connection does not reuse app login/database credentials. Full-slate review and live restart behavior still need verification.

What can be inspected+

Local source separates the research worker, report contract, provenance checks, publication limits and forecast evaluation. Synthetic tests and actual subscription runs are recorded separately.

R1 correlates one actor at a time. Reads distributed across multiple accounts did not reach the per-actor condition in the documented challenge.

Recorded outcomeDid not alert
